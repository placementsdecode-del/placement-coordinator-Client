# Student community and notifications

Students can see their section in the header and open **My Section** to view basic classmate profiles. **My Groups** separates joined groups from pending invitations. Admins and coordinators use **Groups** to create groups and send in-app invitations. Coordinators can invite active students in their assigned sections to groups they created. Admins manage their organization's groups. Students join only after accepting; reading, deleting, or declining a notification never adds membership.

The notification bell supports unread counts, read/unread toggles, mark-all-read, deletion, and invitation responses. It refreshes every 30 seconds while the page is visible, on window focus, and after local actions. Deleted invitation notifications remain accessible as pending invitations in **My Groups**. Accepted/declined responses cannot be overwritten by duplicate requests.

**Tasks** and **Announcements** use the persisted work editor (task, homework, activity, or announcement). Save a draft or choose **Publish and notify**. Assessments also have **Publish and notify** after creation. Publishing captures the active students assigned to the selected sections. Drafts do not generate notifications. Students see published details through **Assigned Work** and the corresponding work-category pages; assessment answers are excluded. Assessment attempts and task submissions are separate work, not implemented by this community feature.

Notification delivery is reconciled from durable invitation and publication records when the inbox loads. Unique recipient/event keys prevent duplicates, and insertion-only updates preserve read/deleted states. Publication and its audience are stored in the same document; a failed delivery request can be retried without losing the event. Existing historical published assessments without audience snapshots are not automatically backfilled.

All HTTP calls use domain services and the shared API client. Models: Group, Notification, AssignedWork, plus publication audience/timestamp fields on Assessment. API routes are documented in Swagger under Student Community, Groups, Notifications, and Assigned Work. Deploy client and server together.

Validation: isolated MongoDB and real HTTP integration tests cover tenant/ownership rules, private section profiles, consent, notification persistence and concurrent delivery, draft/publish behavior, and answer redaction. Optional Chromium tests exercise admin creation, student acceptance and reload, homework publication, notification actions, linked work, and mobile width. Run `cd server && node --import tsx tests/community.integration.ts`. To include browser tests, start the client on port 5173 and set `PLAYWRIGHT_MODULE` to an installed Playwright package. The test creates and removes its own temporary MongoDB data directory on localhost port 27963; no configured application database is used.
